1. 结论摘要

1. 同规格下，EKS 与 EC2 的写入性能基本持平：瓶颈都在数据盘吞吐（gp3 默认 125 MiB/s）。 W1 服务端批量导入为 24.1 万行/秒，EC2 为 24.7 万行/秒（−2.5%）。W2 批量写入在 c=1/8 时相差不到 4%，c=4/16 时 EKS 反而高 7–16%，这在磁盘排队造成的波动范围内。 W3 小批量写入、W4 物化视图管道、insert_quorum=2 的差异都在 ±6% 以内。 两种部署用的是同一种 EBS 卷（gp3、xfs、3000 IOPS / 125 MiB/s）和同样的机型，经 VPC CNI 访问 pod IP 也没有额外的网络跳数，所以写入链路没有可测量的容器开销。
建议：与 EC2 一样，生产环境把 DataVolumeThroughput 提高到约 300 MiB/s。在 EKS 上，这可以通过更新堆栈参数在线完成（VolumeAttributesClass），不需要重启 pod。
2. CPU 密集的并发读取比 EC2 低 5–13%，与 pod 可用 CPU 的差距一致。 c=32 时，Q1–Q6、Q8 的 QPS 比 EC2 低 5–12%，单副本混合负载低 13%。 原因是 Guaranteed QoS 下 ClickHouse pod 的 CPU 上限为 7.1 vCPU（节点可分配 7.91 vCPU，再减去 DaemonSet 预留 0.8 vCPU），比 EC2 整机的 8 vCPU 少 11%。 ClickHouse 仍按 max_threads = 8 起线程，CPU 跑满时会被 CFS 配额限流。 单并发（c=1）的 p50 延迟大多与 EC2 相同或更好（Q1 −9%、Q2 −27%），说明单个查询本身没有变慢，只是总算力少了。
两副本混合负载为 12.9 QPS，比 EC2 高 8.7%，此时两个副本都没有跑满，CPU 上限不是瓶颈。
建议：
  • 读多写少的集群可以选大一号的机型，DaemonSet 的固定开销占比会随之下降；
  • 或者把 ClickHouseCpu 设为整数，并在 profile 中设置 max_threads 等于这个值，避免被限流。
3. Q7（按 trace_id 点查）c=32 低 32%，主要来自数据布局不同，而不是平台差异。 这条查询没有可用的索引，会扫描大量 granule。EKS 每次查询平均读约 154 万行，EC2 约 90 万行（clickhouse-benchmark 的 RPS / QPS）。 两次测试结束时，part 的合并状态不同，跳过的 granule 数也就不同，再叠加第 2 条的 CPU 上限，结果就差了约三分之一。c=1 的 p50 是 26 ms 对 21 ms。
建议（两种部署都适用）：为 trace_id 加 bloom_filter 跳数索引，见运维手册第 8 节。
4. 存储大小与压缩比相同（±3%），复制和 Keeper 行为一致。 每副本压缩后 24.7 GiB，EC2 为 24.0 GiB；压缩比 3.27×，EC2 为 3.36×。差异来自测试结束时 merge 的进度。 两个副本的行数一致；物化视图管道的逐行哈希校验一致；写入结束后，副本追平的时间也与 EC2 在同一量级。
5. EKS 方案的运维验证（部署过程中实测）。
  • EKS Pod Identity：VPC CNI、EBS CSI、CloudWatch Agent、LB Controller 和 ClickHouse 都通过 Pod Identity 获取凭证，没有 OIDC provider，也没有 IRSA。 用 Pod Identity 凭证做的全量和增量 BACKUP 都写入了 S3；从增量恢复 510 万行，哈希与原表一致。
  • 26.8 默认禁止查询中的 S3 使用服务器自身的凭证。备份和恢复语句需要加 s3_allow_server_credentials_in_user_queries = 1，备份脚本已按版本自动添加。EC2 方案在 26.8 上也同样需要。
  • CloudWatch 告警：封锁 r2 所在节点并删除其 pod，约 3.5 分钟后 ServerUp 进入 ALARM，SNS 通知发送成功；解除封锁后 pod 在原 AZ 挂回原 EBS 卷，告警恢复。
  • 堆栈更新（安装器脚本变化，加上 metric_log 的 TTL 配置变化）由 operator 逐个 host 滚动重启。PodDisruptionBudget 的 maxUnavailable=1 生效，数据和 PVC 保持不变。
6. 选型建议。 EKS 方案的性能与 EC2 处于同一水平：写入几乎相同，CPU 密集的读取约低 10%，这部分可以用更大的机型或整数 CPU 配置弥补。 它适合已经有 EKS 平台、希望用 Kubernetes 统一运维的团队。代价是：
  • EKS 控制面约 $73/月，加 2 台 system 节点；
  • 多了 operator、add-on 和 Kubernetes 版本这些需要维护的组件。
没有 Kubernetes 运维能力的团队，EC2 方案的组件更少、单节点算力更完整。

部署方式：本仓库的 EKS 一键模版 templates/clickhouse-eks.template.json，参数见 examples/eks-perf-params.json。ClickHouseVersion = 26.8.24.9，EKS 1.36，Altinity clickhouse-operator 0.27.4。 集群部署在 EC2 测试所用的 VPC 和 3 个私有子网中（CreateVpc=false），节点规格与 EC2 测试相同：

  • 测试期间 Monitoring=CloudWatch（Container Insights 加 ClickHouse 指标上报），EnableBackup=true（压测期间没有执行备份）。
副本跨 AZ（us-west-2a / us-west-2b）。压测客户端与 EC2 测试相同：同 VPC 内一台独立的 m7g.2xlarge（us-west-2a），用原生协议 9000 端口直连 pod IP（VPC CNI），不经过 NLB； 写入在两个副本之间交替分发，读取默认只打 ch-s1-r1（"2 replicas" 场景除外）。脚本、表结构、数据量和查询与 EC2 测试完全相同。 基准对比数据：perf/results（EC2，ClickHouse 26.8.24.9）。

表结构

按业务方提供的 token_hub 建表 DDL 创建 token_hub.t_billing_records（ReplicatedMergeTree，PARTITION BY toYYYYMM(created_at) ORDER BY (kafka_meta_event_type, created_at, user_id)） 和 token_hub.t_billing_records_mv（TO 物化视图，从 Kafka 源表解析 JSON）。与原 DDL 的差异（详见 perf/sql/01_schema.sql）：

  • 所有语句加了 ON CLUSTER '{cluster}'，两个副本同时建表。
  • Kafka 源表 t_billing_events_kafka_source 改为同结构的 ENGINE = Null：生产 Kafka（aliyuncs.com）从 AWS 不可达；向 Null 表 INSERT 会像 Kafka 消费一样触发物化视图，因此可以压测 MV 管道本身。
  • 原 MV DDL 在 ClickHouse 26.8 上执行失败：MV 输出列 client_ip、forwarded_for 在目标表中不存在（Code: 8 THERE_IS_NO_COLUMN）。在 25.8.33.6 上复测，报同样的错误。测试中从 MV 中删掉了这两列，落表数据与原来完全一致。部署到 25.8 或 26.x 前，需要修改生产 DDL：删掉这两列，或在目标表中加上它们。

测试数据

合成数据由参数化视图 bench.gen_billing_rows 生成（perf/sql/02_generators.sql），每行是行号的确定性函数：90 天时间窗口（2026-07-14 → 2026-10-12，4 个月分区）、 10 万用户（强倾斜，少量头部用户贡献大部分请求）、30% 用户属于 5,000 个组织、24 个模型、20 个供应商、97% 成功率、80% 流式；trace_id / 各类 req_id 为随机十六进制字符串（与生产一样不可压缩）。 单行 Native 格式约 327 字节，Kafka JSON 事件约 1,268 字节。

查询 SQL
-- Read workload against token_hub.t_billing_records_mv (a TO-materialized view: SELECTs read t_billing_records).
-- Placeholders ({uid}, {org}, {trace}) are substituted by bench.sh with sampled real values, one query per line.
-- Data window ends 2026-10-12 00:00:00 UTC, so "last 7 days" = since 2026-10-05, "last 24h" = since 2026-10-11.

-- Q1_user_daily_bill: a user's bill per day and model over 30 days (user console)
SELECT toDate(created_at) AS d, model_code, count() AS requests, sum(input_tokens) AS in_tok, sum(output_tokens) AS out_tok, sum(cost) AS total_cost FROM token_hub.t_billing_records_mv WHERE kafka_meta_event_type = 'billing_record' AND created_at >= '2026-09-12 00:00:00' AND user_id = {uid} GROUP BY d, model_code ORDER BY d, model_code

-- Q2_user_recent_records: newest 50 records of a user in the last 7 days (records list page)
SELECT id, created_at, model_code, input_tokens, output_tokens, cost, status, t_first_content, total FROM token_hub.t_billing_records_mv WHERE kafka_meta_event_type = 'billing_record' AND created_at >= '2026-10-05 00:00:00' AND user_id = {uid} ORDER BY created_at DESC LIMIT 50

-- Q3_org_monthly_summary: an organization's September usage by model (org billing)
SELECT model_code, currency, count() AS requests, sum(input_tokens + output_tokens) AS tokens, sum(cost) AS total_cost FROM token_hub.t_billing_records_mv WHERE kafka_meta_event_type = 'billing_record' AND created_at >= '2026-09-01 00:00:00' AND created_at < '2026-10-01 00:00:00' AND org_id = {org} GROUP BY model_code, currency ORDER BY total_cost DESC

-- Q4_hourly_dashboard_24h: platform dashboard, last 24h per hour and model, with TTFT p95 and error rate
SELECT toStartOfHour(created_at) AS h, model_code, count() AS requests, sum(cost) AS total_cost, quantile(0.95)(t_first_content) AS ttft_p95, countIf(status != 'success') / count() AS error_rate FROM token_hub.t_billing_records_mv WHERE kafka_meta_event_type = 'billing_record' AND created_at >= '2026-10-11 00:00:00' GROUP BY h, model_code ORDER BY h, model_code

-- Q5_top_users_7d: top 100 users by spend over the last 7 days
SELECT user_id, count() AS requests, sum(cost) AS total_cost, sum(input_tokens + output_tokens) AS tokens FROM token_hub.t_billing_records_mv WHERE kafka_meta_event_type = 'billing_record' AND created_at >= '2026-10-05 00:00:00' GROUP BY user_id ORDER BY total_cost DESC LIMIT 100

-- Q6_provider_errors_24h: error rate and latency per provider over the last 24h (supplier monitoring)
SELECT provider_id, count() AS requests, countIf(status != 'success') AS errors, round(errors / requests, 4) AS error_rate, quantiles(0.5, 0.99)(total) AS total_ms FROM token_hub.t_billing_records_mv WHERE created_at >= '2026-10-11 00:00:00' GROUP BY provider_id ORDER BY error_rate DESC

-- Q7_trace_lookup: find one request by trace_id (not in the sorting key: worst case, full scan)
SELECT * FROM token_hub.t_billing_records_mv WHERE trace_id = '{trace}' LIMIT 1

-- Q8_monthly_model_revenue: whole-September revenue by model and currency (finance report, full month scan)
SELECT model_code, currency, count() AS requests, sum(cost) AS total_cost, sum(toDecimal128(cost, 0) * discount_rate) AS discounted FROM token_hub.t_billing_records_mv WHERE kafka_meta_event_type = 'billing_record' AND created_at >= '2026-09-01 00:00:00' AND created_at < '2026-10-01 00:00:00' GROUP BY model_code, currency ORDER BY total_cost DESC

6. 资源使用（system.metric_log / CloudWatch）

虚线标出各测试阶段（位置取该阶段第一条结果的时间，近似阶段开始）。写入阶段 CPU 只有 10–30%，数据盘写入却长时间顶在 125 MiB/s；读取阶段正好相反，CPU 接近 100%，磁盘几乎空闲。

7. 测试方法与复现

  • perf/sql/01_schema.sql — 建表 DDL（来自业务方提供的 token_hub DDL，差异见第 2 节）
  • perf/sql/02_generators.sql — 合成数据生成器（参数化视图）
  • perf/sql/03_read_queries.sql — 读取负载 Q1–Q8
  • perf/bench.sh — 在压测机上执行全部写入 / 读取测试，结果写入 /opt/bench/results
  • perf/fetch-metrics.sh — 拉取实例 / 卷信息和 CloudWatch 指标；perf/report.js — 生成本报告

说明：W2 / W3 / W4 中同一批数据文件在不同并发档位下重复写入，并关闭了 insert_deduplicate，因此表中这部分数据存在重复的 id，不影响吞吐测量。 写入延迟和内存取自两个副本的 system.query_log；读延迟来自 clickhouse-benchmark 的客户端统计（包含网络往返），精度 1 ms。
